# LLM 기반 알라딘 사용자 리뷰 분석

> 한국어 사용자 리뷰를 LLM으로 범주형 데이터로 구조화하고, 반복적으로 나타나는 앱 사용 불편을 탐색한 프로젝트입니다.

## 1. 프로젝트 개요

AI POC 클리닉에서 알라딘의 서비스 경험을 탐색하는 과정에서, 사용자 리뷰를 활용해 앱의 UI/UX 관련 불편을 분석했습니다.

Google Play Store에서 관련도 순으로 리뷰 500개를 수집하고, 이 중 별점 1~2점인 부정적 리뷰 350개를 분석 대상으로 선정했습니다. 이후 **4비트 양자화된 Qwen2.5-7B-Instruct**와 few-shot 프롬프트를 활용해 리뷰를 사전에 정의한 문제 범주로 분류했습니다.

이 프로젝트는 모델을 새로 학습하는 작업이 아니라, **사전학습된 LLM을 활용하여 자연어 데이터를 비교·집계 가능한 형태로 변환하는 분석 파이프라인을 구성한 작업**입니다.

| 항목 | 내용 |
|---|---|
| 활동 | AI POC 클리닉 |
| 수행 기간 | 2026.08.05~2026.09.11 |
| 팀 규모 | 3명 |
| 담당 역할 | 데이터 분석 |
| 대상 데이터 | 알라딘 앱의 Google Play Store 리뷰 |
| 분석 대상 | 수집 리뷰 500개 중 별점 1~2점 리뷰 350개 |
| 주요 기술 | Python, Pandas, PyTorch, Transformers, bitsandbytes |
| 모델 | Qwen2.5-7B-Instruct |
| 추론 환경 | Google Colab의 CUDA GPU 환경 |

## 2. 문제 정의

기업과 서비스에 대한 문제의식을 구체화하려면 사용자가 실제로 어떤 불편을 보고하는지 확인할 필요가 있었습니다. 공개 사용자 리뷰는 이러한 경험을 살펴볼 수 있는 자료였지만, 자유로운 자연어로 작성되어 있어 그대로는 문제 유형별 비교와 집계가 어려웠습니다.

같은 불편도 서로 다른 표현으로 나타나고, 하나의 리뷰에 검색·버튼 반응·결제 등 여러 문제가 함께 서술될 수 있습니다. 따라서 단순한 키워드 검색 대신, 리뷰의 문맥을 읽고 일정한 기준에 따라 구조화하는 방법을 탐색했습니다.

핵심 분석 질문은 다음과 같습니다.

- 부정적 리뷰에서 UI/UX 관련 불편은 얼마나 나타나는가?
- UI/UX 관련 리뷰에는 어떤 문제 유형이 반복되는가?
- 자연어 리뷰를 사전에 정의한 범주로 변환하고, 분류 결과를 검토할 수 있는 형태로 저장할 수 있는가?

분석 범위는 **선정한 리뷰에 나타난 앱 사용 경험**입니다. 알라딘의 브랜드 문제 전체를 검증하거나, 전체 사용자의 불편 비율을 추정하는 것은 목표에 포함하지 않았습니다.

## 3. 접근 방법

### 자연어 리뷰를 범주형 데이터로 변환

LLM을 이용해 각 리뷰에서 다음 정보를 추출했습니다.

| 필드 | 의미 |
|---|---|
| `is_ui_ux_issue` | UI/UX 관련 문제 여부 |
| `ui_ux_topic` | 사전에 정의한 문제 범주 |
| `primary_reason` | 분류에 대한 모델의 설명 |

리뷰마다 구조화된 결과를 생성하고 원문·별점·작성일과 결합하여, 범주별 집계와 원문 대조가 가능한 데이터로 만들었습니다.

모델이 생성한 설명은 분류를 검토하는 데 활용할 수 있지만, **설명이 존재한다는 사실만으로 분류의 정확성이 보장되지는 않습니다.**

### 분류 체계

UI/UX 관련 리뷰는 다음 네 가지 범주 중 하나로 분류하도록 설정했습니다. 그 외 문제는 `NON_UI_UX`로 구분했습니다.

| 범주 | 내용 |
|---|---|
| `SEARCH_NAVIGATION` | 책·중고 상품 탐색의 어려움, 숨겨진 탭, 복잡한 탐색 동선 |
| `LAYOUT_CLUTTER` | 과밀한 텍스트와 화면 구성, 가독성 저하, 시각적 혼잡 |
| `INTERACTION_AFFORDANCE` | 버튼 무반응, 클릭 가능한 요소의 인지 어려움, 터치 영역 문제 |
| `CART_CHECKOUT_UX` | 복잡한 장바구니 선택 흐름, 이동 과정에서 선택 상태가 유지되지 않는 문제 |
| `NON_UI_UX` | 앱 충돌, 서버 지연, 결제 인증 오류, 배송 등 위 UI/UX 범주 외 문제 |

이 분류 체계는 분석을 위한 조작적 정의입니다. 특히 버튼 무반응과 시스템 오류처럼 서로 겹칠 수 있는 현상은 리뷰의 서술만으로 명확하게 구분하기 어려울 수 있습니다.

### 분석 파이프라인

1. **리뷰 수집**  
   Google Play Store에서 한국어·한국 지역의 관련도 순 리뷰 500개를 수집했습니다.

2. **분석 대상 선정**  
   별점 1~2점 리뷰를 선별했습니다. 원본 실행에서는 350개가 선정되었습니다.

3. **모델 로드**  
   Qwen2.5-7B-Instruct를 NF4 4비트 양자화로 로드했습니다. FP16 연산과 이중 양자화 설정을 사용했습니다.

4. **리뷰별 추론**  
   영어 지시문과 few-shot 예시를 포함한 프롬프트에 한국어 리뷰를 입력하고, 영어 JSON 출력을 요청했습니다.

5. **구조화 및 저장**  
   생성된 응답을 JSON으로 파싱하고, 분류 결과와 원문 정보를 결합했습니다.

6. **집계 및 결과 확인**  
   UI/UX 분류 비중과 세부 범주별 건수를 집계하고 CSV로 저장했습니다.

이 노트북은 외부 LLM API를 호출하지 않고, **Transformers로 모델을 직접 로드하여 추론**합니다.

## 4. 모델 선택과 시행착오

### 4.1. 소형 모델의 출력 품질 문제

수백 개의 리뷰를 처리하기 위해 처음에는 Qwen2.5-5B-Instruct를 사용했습니다. 그러나 당시 실행에서는 리뷰 내용에 충실하지 않은 응답과 환각이 나타나, 분석에 활용할 만큼 안정적인 출력을 얻기 어려웠습니다.

이를 개선하기 위해 더 큰 모델인 Qwen2.5-7B-Instruct를 사용하고자 했습니다.

이는 프로젝트 진행 중 관찰한 경험이며, 소형 모델과 7B 모델의 성능을 정량적으로 비교한 실험은 아닙니다.

### 4.2. Colab 메모리 제약과 4비트 양자화

7B 모델을 일반적인 방식으로 로드하려 했으나, 당시 Colab 환경에서는 메모리 제약으로 모델을 로드하지 못했습니다.

이를 해결하기 위해 **4비트 양자화**를 적용했습니다. 모델 가중치의 메모리 사용량을 줄여 제한된 GPU 환경에서도 모델을 로드하고 리뷰 분석을 실행할 수 있었습니다.

이 과정에서는 모델의 크기뿐 아니라, 실제 실행 환경의 자원 제약을 고려해 추론 구성을 선택하는 것이 중요했습니다.

### 4.3. 출력 언어의 불안정과 영어 지시문

양자화된 모델을 실행하는 과정에서 한국어 출력이 불안정하고, 중국어로 전환되는 현상이 나타났습니다.

이에 리뷰 원문은 한국어로 유지하되, **분류 지시문과 출력 형식을 영어로 작성**하는 방식으로 조정했습니다. 최종 구현에서는 영어 JSON으로 범주와 분류 이유를 생성하도록 했습니다.

다만 출력 언어 문제가 양자화 때문에 발생했는지, 프롬프트 구성이나 모델의 언어별 특성 때문인지를 분리하여 검증하지는 않았습니다. 따라서 영어 사용은 당시 실행에서 선택한 대응 방법이며, 일반적인 성능 개선 효과로 주장하지 않습니다.

### 4.4. Few-shot 예시로 분류 기준 전달

범주 이름과 설명만 제시하는 대신, 리뷰와 기대하는 JSON 응답의 예시를 프롬프트에 포함했습니다.

이를 통해 모델에 다음을 구체적으로 전달하고자 했습니다.

- 어떤 서술을 각 범주에 포함할지
- UI/UX 문제와 그 외 문제를 어떻게 구분할지
- 분류 결과를 어떤 JSON 형식으로 반환할지

Few-shot 예시는 사람이 의도한 분류 기준을 전달하기 위한 장치입니다. 별도의 정답 데이터셋이나 비교 평가가 없으므로, 이를 통해 인간 수준의 판단이나 정확도를 달성했다고 주장하지 않습니다.

## 5. 분석 결과

첨부된 원본 노트북의 저장된 실행 출력에서 다음 결과를 확인했습니다.

- 수집 리뷰: **500개**
- 분석 대상 부정적 리뷰: **350개**
- UI/UX 관련으로 분류된 리뷰: **111개**
- 분석 대상 내 UI/UX 분류 비중: **31.7%**

### UI/UX 세부 범주 분포

| 범주 | 리뷰 수 | UI/UX 분류 리뷰 111개 내 비중 |
|---|---:|---:|
| 버튼 반응·상호작용 인지 (`INTERACTION_AFFORDANCE`) | 46 | 41.4% |
| 검색·탐색 (`SEARCH_NAVIGATION`) | 37 | 33.3% |
| 장바구니·구매 흐름 (`CART_CHECKOUT_UX`) | 16 | 14.4% |
| 화면 구성·가독성 (`LAYOUT_CLUTTER`) | 12 | 10.8% |

**31.7%의 분모는 분석 대상 부정적 리뷰 350개이며, 표의 범주별 비중은 UI/UX로 분류된 111개를 기준으로 합니다.** 반올림으로 표의 비율 합계는 100%와 다를 수 있습니다.

UI/UX 분류 리뷰에서는 버튼·터치 등 상호작용 문제와 검색·탐색 불편이 상대적으로 많이 나타났습니다. 이 결과는 해당 영역을 후속 사용성 검토 대상으로 살펴볼 근거가 됩니다.

다만 리뷰를 분류한 결과만으로 실제 오류의 원인, 전체 사용자에게 미치는 영향, 개선 우선순위를 확정할 수는 없습니다.

## 7. 한계

### 표본의 선택 편향

관련도 순으로 수집한 리뷰 중 별점 1~2점만 분석했습니다. 따라서 결과는 불편 유형 탐색을 위한 자료이며, 전체 사용자나 전체 리뷰를 대표하지 않습니다.

### 임의로 설정된 분류 기준

분류 컬럼은 사람의 판단과 직관 하에 임의로 형성되었습니다. 따라서 객관적인 기준으로 보기 어렵습니다.

### JSON 파싱 실패 처리

원본 구현은 JSON 파싱에 실패하면 해당 리뷰를 `NON_UI_UX`로 처리합니다. 따라서 기술적인 출력 실패가 실제 비UI/UX 분류와 섞일 수 있으며, 집계에 영향을 줄 가능성이 있습니다.

### 정량적 분류 평가 부재

원문과 분류 결과를 대조해 검토했으나, 별도의 정답 데이터셋을 기반으로 정확도·정밀도·재현율을 측정하지 않았습니다. 노트북의 샘플 출력 확인 역시 전체 분류 결과의 검증을 대신하지 않습니다.

## 8. 배운 점

이 프로젝트에서는 자연어 데이터를 분석 가능한 형태로 바꾸는 과정이 단순한 모델 호출보다 더 넓은 설계를 요구한다는 점을 경험했습니다.

- **분류 기준 설계:** 프롬프트를 통해 모델에 무엇을 구분하도록 요청할지 명확히 정의해야 합니다.
- **실행 가능성 확보:** 모델 선택과 함께 GPU 메모리 등 자원 제약을 고려해야 합니다.
- **검증 가능성 확보:** 분류 결과를 원문과 함께 저장하고, 모델 오류와 실제 분석 결과를 구분해야 합니다.
